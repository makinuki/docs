MakiNuki (巻抜き) is an open-source manga reader stack where scrapers compile to WebAssembly and run inside an Extism sandbox. ABI 1 is the frozen contract that governs how these plugins talk to the host. Hosts mediate every network request, storage operation, and log line. Plugins export a fixed set of functions to search, detail, and deliver manga. This page introduces the five architectural principles and the JSON-over-memory model that every ABI 1 source must follow.

## Architectural Principles

1. **Host-Sandboxed Execution**<br />Scrapers run as compiled `.wasm` modules managed by the Extism runtime. They have zero direct access to OS sockets, file systems, or DOM APIs.
2. **Inverted I/O (Host-Driven Networking)**<br />All HTTP requests, cookie storage, and environment bridges are delegated to the host runtime via host imports in the `makinuki` namespace.
3. **Language-Agnostic Source Development**<br />Scrapers can be written in any language supported by Extism PDKs (TypeScript, Go, Rust, Python, C, Zig) as long as they compile to standard `.wasm` exporting the MakiNuki ABI.
4. **Declarative UI Filtering**<br />Filter systems are emitted as schema arrays. Host applications dynamically generate native UI components (dropdowns, tri-state checkboxes, search fields) without hardcoding source specifics.
5. **Two-Tier Image Delivery**<br />Standard image streams bypass WASM memory via direct CDN URLs. Scrambled or sliced images are routed through an optional WASM `unscramble_image` hook only when necessary.

## Extism + JSON-over-Memory Model

ABI 1 exchanges data as JSON strings passed across the Extism memory boundary. Host functions live under the `makinuki` namespace. Plugin functions accept and return serialized JSON, except `unscramble_image`, which moves raw bytes.

Because the contract is memory-bound, hosts enforce budgets: **64 MB per instance** and **16 MB per image buffer** (8192 x 8192 px max). If a plugin exceeds these limits, the host rejects the call with `MEMORY_LIMIT_EXCEEDED`.
