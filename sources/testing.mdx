The conformance test runner exercises every plugin export against live source websites and asserts payloads against the canonical JSON Schemas shipped in `@makinuki/spec`. Because tests hit real endpoints, a network connection is required and results may vary from one network to another.

Beyond checking schemas, the runner enforces contract rules hosts rely on:

- Every URL it inspects (search item, chapter, and page URLs) must be an absolute http(s) URI.
- Page indexes must be sequential from zero.
- A page marked scrambled must carry descramble metadata.
- The runner proves the page-schema contract itself before any plugin runs, so a schema regression fails fast.
- When a plugin exports the optional `get_settings`, the runner validates the payload against the settings schema, requires unique setting ids and a text-shaped `base_url` setting, and proves the storage wiring persists values through a round-trip write.
- The pass line reports which optional exports (`get_settings`, `unscramble_image`) a plugin carries. Plugins without settings still pass.

## Run the tests

Test every built plugin in `dist/`:

```bash
pnpm test
```

Scope the run to one or more specific plugins by passing their ids as positional arguments:

```bash
pnpm test mangadex
pnpm test mangadex asurascans cubari
```

## Per-plugin test fixtures

Each source can pin the locators the runner exercises in `sources/<id>/test.json`. The file is optional and supports four fields:

| Field | Type | Purpose |
| --- | --- | --- |
| `search` | string | Query passed to the `search` export |
| `details` | string | Manga id passed to `get_details` |
| `pages` | string | Chapter id passed to `get_pages` |
| `challengeGated` | boolean | Flags that the source requires a browser to reach |

If `test.json` is absent, the runner uses a default query and probes the first few search results for a title that carries chapters.

## Challenge-gated sources

Some sources sit behind an anti-bot challenge (such as Cloudflare) that a headless runner cannot solve. Hosting and CI networks are challenged far more often than desktop connections, so a source can work perfectly from a browser and still be unreachable from the test pipeline.

A source may declare `rateLimit` and `retry` transfer hints in its metadata. These are host guidance, not requirements: hosts may honor, cap, or let users override them. The runner does not enforce these values, but `pnpm generate-index` carries whatever a plugin declares into the registry entries in `dist/index.json`.

When a plugin sets `challengeGated: true` in its `test.json`, the runner reports `SKIP` instead of failing, as long as the plugin still answers with a well-formed envelope carrying the `CLOUDFLARE_BLOCKED` error code. Any other failure mode (a parse error, a different error code, or a non-conforming response) still fails the run, so regressions are caught.

<Warning>
  `challengeGated` is not an excuse to ignore failures. The plugin must still emit a correct `CLOUDFLARE_BLOCKED` envelope. A broken plugin still fails.
</Warning>

## Passing browser credentials

To run the full conformance check against a gated source, solve the challenge in a real browser, copy the user agent and clearance cookie, and pass them as environment variables:

```bash
MAKINUKI_TEST_UA="Mozilla/5.0 (X11; Linux x86_64) AppleWebKit/537.36 ..." \
MAKINUKI_TEST_COOKIE="cf_clearance=<your_clearance_value>" \
  pnpm test weebcentral
```

The runner sends these values on outgoing requests, letting the source see a browser-like identity and bypass the challenge.
